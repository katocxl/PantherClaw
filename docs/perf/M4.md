# M4 latency measurements

**Date:** 2026-10-09. **Measured by:** Claude Code. **Target:** SIMULATED (`pantherclaw-sim payments`). No real money moved.

This is the measurement that G0 M4 part 2, design decision 21, asks of the exit slice: `Authorize` on the decision pipeline, measured as [M1.5](M1.5.md) was.

## Summary

| SLO (ARCHITECTURE §15) | Result on the development laptop |
|---|---|
| Authorize p99 ≤ 25 ms at 1k rps, 2 vCPU, co-located | **Not met.** Co-located at 50 rps: p50 17 ms, p99 79 ms. At 100 rps half the requests reach the gateway's 2 s timeout (fail-closed `503`), and at 300 rps every one does. |
| Gateway overhead p99 ≤ 35 ms at 1k rps | **Not met.** p99 117 ms at 50 rps co-located. |

As in M1.5, a laptop measurement cannot validate the SLO. But M4 is clearly slower than M1.5 on the same machine. The main cause is visible in the database counters: the decision pipeline makes about **40 database transactions per accepted refund** (M1.5 `Authorize` made about 13 round trips in total). Every read through the pipeline reader (containment, definition, policy, run, agent, grant chain, guardrails, facts, budget usage, dedupe claim) opens its own tenant transaction, and the finalization adds its own lookup, prepare and finalize transactions. Each transaction costs several round trips (`BEGIN`, setting the tenant, the queries, `COMMIT`).

The money invariants held through every overload (see below).

**Recommended follow-up** (a separate slice; it changes no contract):
1. Read every input of one evaluation in **one read-only transaction** (one snapshot instead of about ten). This also gives the pipeline a consistent view, which today only the finalization's re-check guarantees. **Done 2026-10-10**, see [one snapshot per evaluation](#2026-10-10-one-snapshot-per-evaluation).
2. Fold the finalization's first `Lookup` into that read, and its second one into `Finalize`. **Done 2026-10-10**, in the same change.
3. Re-measure, co-located, on Linux with local NVMe, which M1.5 also still needs. [ADR-0015](../adr/0015-budget-settlement-off-the-hot-row.md) (settling budgets off the hot row) remains proposed: every refund of one grant still updates the same task-budget account row.

## Machine and setup

| | |
|---|---|
| Laptop | Intel Core i7-11370H (4 cores, 8 threads), Windows 11 Home 10.0.26300, the same machine as M1.5 |
| Shared load | Other Claude Code sessions were building and running tests at the same time, so the numbers are noisy. |
| PostgreSQL | 17 (Debian, the compose image), a **private** container for this measurement (`pantherclaw-m4-perf`, removed afterwards) in Docker Desktop. Defaults: `synchronous_commit` on, `shared_buffers` 128 MB. |
| Org | Seeded by `pantherclaw-server dev seed`: the reference package (active), a development fact provider, a grant with a USD 100,000,000 task budget, and a run bound to it. No policy is published, and there are no guardrails. |
| Load | `pantherclaw-sim load --unique --facts-key-file …`: open loop, constant arrival rate, 30 s measured after a 5 s warm-up. Each request refunds a distinct (charge, amount) pair, because repeat protection parks identical irreversible refunds (HR-007); the charges are reported as refundable before the run and every 2 minutes. "authorize" and "gateway_overhead" come from the gateway's `Server-Timing` (overhead = total − target time). The server's pool has 20 connections; logging is at `warn`. |

Two placements, as in M1.5:
- **W — Windows-native processes.** Postgres is behind Docker Desktop's port forwarding.
- **L — Linux binaries co-located.** Server, gateway, target and load driver run in the database container's network namespace, so Postgres is on loopback.

### Database transactions per refund

On W at 10 rps, the database committed 14,671 transactions during a run of 350 refunds (warm-up included). An idle server commits about 17 per second (sweeper, job queue, chainer), about 615 over that run. That leaves **about 40 transactions per accepted refund**: identity and run binding, the pipeline's reads, the finalization, `BeginDispatch` and `RecordExecution`.

### Money invariants after the overloads

After all runs (6,468 permits, many of them under timeouts), checked directly in the database:
- The grant's task-budget account shows **spent 52,674.09 USD over 6,320 refunds and nothing reserved**. That is exactly the sum and count of its `COMMITTED` reservations; no reservation is `HELD`.
- Every permit ended `DISPATCHED` (6,320) or `RELEASED` (148, expired before dispatch and released by the sweeper). None is left `ISSUED`, `DISPATCHING` or `UNKNOWN`.
- No refund was dispatched without a decision. Timeouts at the gateway fail closed, and decisions the Authority finished after the gateway gave up expired unused.

## Method notes

- `dev seed` with `--facts-key-out`, then `pantherclaw-sim load --unique --facts-key-file <key>` (the driver reports the facts itself). Without `--unique`, every refund after the first is parked (`RECONCILIATION_REQUIRED`), as HR-007 intends. Each run tags its charges, so a second run never repeats the first one's refunds.
- The co-located runs used static Linux binaries in `docker run --network container:<database>`, with secret files copied in with mode 0600 (bind-mounted Windows files fail the 0600 check), as in M1.5.

## 2026-10-10: one snapshot per evaluation

**Change:**
- One evaluation now reads all its inputs in **one** `REPEATABLE READ, READ ONLY` tenant transaction (`pgauthority.Reader.Snapshot`): containment, definition, connection, run, agent, grant chain, guardrails, policy, facts, budget usage and the dedupe claim.
- The finalization's first `Lookup` runs in that snapshot, and the second is gone (the result keeps the receipt that `Finalize` recorded).
- The finalization itself is unchanged: it still re-checks the epoch, grants and guardrails under `FOR SHARE` and reserves budgets as before (HR-048, and the reservation check at `COMMIT` from #121).

**Method.** Placement L as above, with these differences:
- Each run used a fresh private PostgreSQL 17 container, with `pg_stat_statements` loaded to count statements.
- Two binary sets were built from the same commit (`0ecf8b8`), without and with the change, and run in ABBA order (before, after, after, before).
- Each run began with a 10 rps run (the "first run after start-up"), then 50, 100, 200 and 300 rps on the same stack.
- **The laptop was busier than on 2026-10-09:** CPU at 100%, and the shared test cluster used about 2 CPUs for other sessions' tests. Latency near the overload point is therefore very noisy; the transaction counts are not affected.

### Transactions per accepted refund

At 10 rps, 350 refunds per run (warm-up included). The idle rate was measured on the same stack just before each run (about 24 per second) and subtracted, as above.

| | before | after |
|---|---|---|
| Database transactions (`pg_stat_database`), 3 runs each | 41.8, 42.3, 42.5 | 18.3, 18.4, 18.5 |
| Tenant transactions (`InTenantTx`), background included | 21.6 | 9.6 |
| Of which the pipeline's reads and the finalization's lookups | 13 | 1 |

Each tenant transaction also costs an implicit transaction when its connection goes back to the pool (`RESET ALL`), so 12 fewer tenant transactions remove about 24 counted transactions. What remains per refund:
- identity and run binding;
- the snapshot, `Prepare`, `Finalize`, `BeginDispatch` and `RecordExecution`;
- their `RESET ALL`s.

### Closed loop: `BenchmarkRefund`

`go test -tags integration -bench BenchmarkRefund -benchtime 1000x ./internal/authority/adapters/pgauthority/`, run as a Linux binary in the network namespace of a private PostgreSQL container. Each refund runs `Authorize`, `BeginDispatch` and `RecordExecution` against one task budget, from a fixed number of workers, so the code paths are compared without open-loop overload. Three pairs, alternating; `Authorize` p50 / p99 in ms:

| Pair | 1 worker, before | 1 worker, after | 8 workers, before | 8 workers, after |
|---|---|---|---|---|
| 1 | 33.8 / 79.7 | 20.3 / 62.5 | 131.7 / 445.9 (31/s) | 54.0 / 216.6 (69/s) |
| 2 | 20.0 / 53.9 | 15.6 / 51.1 | 33.7 / 100.7 (131/s) | 24.3 / 108.1 (153/s) |
| 3 | 15.5 / 28.8 | 11.9 / 36.2 | 75.3 / 229.9 (57/s) | 64.4 / 355.3 (51/s) |
| Median | 20.0 / 53.9 | **15.6 / 51.1** | 75.3 / 229.9 (57/s) | **54.0 / 216.6 (69/s)** |

- p50 is lower in every pair, by 14–59%.
- p99 and throughput improved in pair 1 and were mixed in pairs 2 and 3; their medians improved.
- Results differ up to 4× from one pair to the next, so these are indications, not precise figures.

- **Below overload** (run 2 against run 1 at 50 and 100 rps): Authorize p50 dropped from about 24 ms to 17 ms. p99 dropped too (492 against 1,140 ms at 50 rps; 445 against 601 ms at 100 rps).
- **At overload** the change does not help, and it can make the collapse sharper. Run 3 collapsed already at 50 rps. Once collapsed, the "after" stack answered nothing within the 2 s timeout, while "before" still accepted a few refunds even at 300 rps. The machine's own load explains part of this: a separate probe of "before" at 50 rps, run during the same busy period, also collapsed.
- **Where the requests wait.** Lock waits were sampled twice a second during 100 rps probes. They are all on the one task-budget row:
  - `ReserveBudgetAccount` (`Finalize`) and `SettleBudgetAccount` (`RecordExecution`);
  - and about a quarter of them `EnsureBudgetAccount`: `Prepare`'s `INSERT … ON CONFLICT DO NOTHING` waits for the row's in-flight updaters.

  Sessions waiting on a lock averaged 6.5 with the change, against 1.7 before. With the pipeline no longer slowed by a dozen pool round trips, more requests reach the hot row at once and queue on its lock. Without a fast-fail lock timeout, that queue outlasts the gateway's 2 s timeout. The same probes with a `READ COMMITTED` snapshot behaved the same, so the isolation level is not the cause.

### Money invariants

After every run, checked in the database:
- each task-budget account's `spent` equals the sum of its `COMMITTED` reservations to the cent, and `reserved` equals its `HELD` ones;
- the only `ISSUED` permits were from the last seconds of the last run, not yet expired when checked;
- no permit is left `DISPATCHING` or `UNKNOWN`.

### Next

1. **Skip `Prepare` when the snapshot already found every budget account and counter row.** The usage read returns their ids. Each refund would then wait on the hot row once before its permit instead of twice, and make one transaction fewer.
2. **[ADR-0015](../adr/0015-budget-settlement-off-the-hot-row.md)**, still proposed. A short `lock_timeout` on the hot row turns queueing into a fast `CANNOT_AUTHORIZE`, and settling off the row halves the waits. With the pipeline cheaper, the hot row is now the limit.
3. **Re-measure on Linux with local NVMe**, on an otherwise idle machine, with `BenchmarkRefund` and `pantherclaw-sim load`.
