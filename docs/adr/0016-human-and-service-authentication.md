# ADR-0016 — Human and service authentication for the control plane

**Status:** Accepted (founder decisions 2026-10-08, M2 G0)

**Context.** SB-2 fixes the methods (OIDC for humans, device flow for the CLI, `private_key_jwt` for services, `pck_` API keys). M2 has to decide how a credential finds its tenant without weakening RLS, who runs the device flow, and what token the CLI and services present to the API.

**Decision.**
1. **Credentials carry their org.** API keys (`pck_<env>_<org>_<secret>`), device codes, refresh tokens, invitation tokens and service-account client ids embed the org id. The server opens a tenant transaction for that org and looks the credential up by SHA-256 under forced RLS. No new SECURITY DEFINER function or global credential index is needed (HR-053 unchanged). Invitation tokens are single-use, expiring random secrets of the same shape; this replaces the "signed" invitations named in BUILD_GUIDE §8, because the stored row is authoritative and a signature would add no integrity.
2. **PantherClaw mediates the CLI device flow.** The CLI talks only to PantherClaw (RFC 8628 shape). PantherClaw is the OIDC relying party toward the IdP (authorization code + PKCE S256, `nonce`, one callback per provider, RFC 9207 `iss`) and links the IdP identity `(iss, sub)` to a user of the org.
3. **PantherClaw issues its own access tokens.** 15-minute EdDSA JWS (`typ: at+jwt`) signed by a dedicated `access_tokens` key, for humans (after device login or refresh) and service accounts (after a client-credentials grant). Every request re-checks that the principal, its session or key, and its org are still active, so revocation is immediate rather than bounded by the token lifetime.
4. **CLI refresh tokens are bound to a device key** generated by the CLI; code exchange and every refresh carry a client assertion signed with it. Refresh tokens rotate; reuse revokes the session. Tokens are kept in a 0600 file in the user's config directory.
5. **Administrators may grant themselves roles**, audited and flagged; Org Admin itself contains no approval, publication or restricted-evidence permission.

**Consequences.** Org ids appear in credentials (they are not secret). IdP access tokens never reach the API; only one IdP client registration is needed and IdPs without device-flow support work. A per-request database check costs one tenant transaction. Device-code phishing remains possible (an attacker can send a victim a code); the confirmation page shows the requesting device and the codes expire after 10 minutes. A stolen credentials file includes the device key; an OS key store is a later upgrade.

**Alternatives.** A second SECURITY DEFINER lookup or a global hash → org index (widens the RLS bypass surface); the IdP's own device flow with a token exchange (needs IdP support and a public client per IdP); passing IdP tokens to every API call (ties revocation and audience to each IdP); server-generated service-account private keys (the server would see them).
