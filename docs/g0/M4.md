### G0 — M4 Authority core, part 1: tool packages, action definitions, ActionIR mapping, CEL policy engine — 2026-10-08

This brief is written before implementation (G0). It lists planned scope for **part 1** of M4 only. Part 1 runs in parallel with M2 (tenancy & service authentication). It therefore covers only the pieces of M4 that depend on neither M2 nor M3, at the domain and application layers.

**Purpose:** give the Authority a reviewed, signed meaning for every operation (tool packages and action definitions), a strict way to turn an MCP tool call or HTTP request into ActionIR (mapping), and a fail-closed CEL policy engine. The decision pipeline (part 2) then composes these with grants, budgets and facts.

**Scope (planned, part 1):**
- `internal/definitions/domain`: action definitions and packages, all pure:
  - **operation and target identity:** type, id pattern, account requirement;
  - **typed material parameters with units:** `money` with allowed currencies, `decimal` and `integer` with a unit from a closed list and bounds, `enum`, `identifier`, `boolean`, `string_list`, and non-material untrusted `text`;
  - **effects, side effects, reversibility** and read/write class;
  - **constraints** the tool can enforce (F100), **prerequisites** (named trusted facts with maximum age), **retry semantics** and **verifier**;
  - **approval template**, whose placeholders may name only canonical material fields (HR-034 groundwork);
  - the **semantic dedupe key**: a list of canonical fields, hashed from their canonical values, and the **assurance metadata** (basis, reviewers, `valid_until`);
  - **mappings** from MCP tools and HTTP routes;
  - **consequence rules** (ConsequenceIR, F405 groundwork: predicted consequences only);
  - the definition **lifecycle** state machine (F394) and the per-org **pin rule**: version pins only move forward (HR-123).
- `internal/definitions/manifest`: the YAML package format (`format: 1`).
  - Strict decoding (HR-100): duplicate keys, anchors, aliases, merge keys, explicit tags, floats, nulls, multiple documents, unknown fields, excessive depth or size are all rejected.
  - Decoded YAML is converted to JSON and decoded with `encoding/json/v2` (`RejectUnknownMembers`).
  - The **definition digest** is `sha256:` + SHA-256 of the RFC 8785 canonical JSON of one definition, mappings included. This is the `definition.digest` that ActionIR pins (PAP-1 §6).
- `internal/definitions/trust`: TUF-style signed metadata.
  - The offline package root (`pclaw-admin keygen --purpose packages`, Day-0 item 6) signs a **targets** document: `version`, `expires`, and for each `name@version` the SHA-256 and length of the exact package bytes.
  - The signature is a compact JWS (EdDSA only, `typ: pc-package-targets+jwt`, kid `packages-root-…`) verified against embedded roots (`roots.json`, empty until Day-0 item 6).
  - Anti-rollback: a metadata version lower than the last one seen is refused, and so is an expired document.
  - Tests use generated test keys only.
- `internal/definitions/app`: the `ImportPackage` use case. It verifies the metadata, matches the package bytes, decodes and validates the package, checks the pin advance, and stores the package. The trust state, packages and pins are behind interfaces (`TrustStore`, `PackageStore`, `PinStore`) and have no tables yet.
- `internal/platform/celenv`: one CEL environment family for mappings, policies and (later) detections.
  - Custom **`pc.Decimal` and `pc.Money`** types: exact arithmetic and comparison; money across currencies is an error.
  - Struct types generated from the action definition schema, so each parameter is typed at check time.
  - Validators: ordering operators on `string`, `bytes`, `double` or `dyn` are rejected at type-check, and so are `double` literals (HR-041). Optional fields need a `has()` guard (HR-042).
  - Parser size and recursion limits, comprehension nesting limit, and estimated-cost and runtime cost limits (HR-043).
- `internal/definitions/mapping`: MCP tool call or HTTP request → ActionIR.
  - The input is strict JSON (duplicate keys rejected; only integer JSON numbers, which become CEL `int`).
  - HTTP paths match a reviewed template on a strict character set.
  - CEL extraction expressions, compiled and type-checked when the package is loaded, produce the target, parameters and destinations. The dedupe key is then computed from the canonical result, never from raw input.
  - Parameters are validated against their declared types. Material amounts are always decimal strings (HR-101); bidi and control characters are rejected (HR-102); a missing or ambiguous value is an error, never a default (HR-103).
  - The result goes through `actionir.Encode`, which gives the canonical form and hash.
- `internal/policy/domain` and `internal/policy/app`: structured rules with kinds `FORBID`, `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP`, `CONSTRAIN` and `ANNOTATE`.
  - Each rule has a scope (operations and environments), a CEL condition, a stable reason code, a requirement or constraint, and labels.
  - Rules are type-checked per operation when a bundle is compiled.
  - Evaluation is fail-closed (HR-040): an error in a FORBID rule gives `DENY`; an error in a REQUIRE or CONSTRAIN rule gives `CANNOT_AUTHORIZE`; a per-evaluation cost budget overrun gives `CANNOT_AUTHORIZE` (HR-043).
  - A CONSTRAIN rule whose constraint the definition does not declare gives `CANNOT_AUTHORIZE` (F100).
  - Composition is deterministic: prohibitions win, requirements combine, and the checklist puts the decisive item first.
  - The policy result is a verdict (`PASS`, `CONSTRAIN`, `REQUIRE_APPROVAL`, `REQUIRE_STEP_UP`, `DENY`, `CANNOT_AUTHORIZE`), not an `ALLOW`. Only a grant (part 2) can allow.
  - A comparison-flipping mutation tester is included (HR-044 groundwork).
  - Bundles are stored behind a `BundleStore` interface.
- A reference package `packages/mock-payments/package.yaml` that describes the M1.5 refund route. It is golden-tested: canonical JSON, definition digest, and the ActionIR produced for fixed inputs.

**Security constraints and design decisions:**
1. **Signatures cover exact bytes.** The targets document lists the SHA-256 and length of the raw package file, so no YAML parser differential can change what was signed. The canonical JSON form is used only for the definition digest.
2. **One offline key, no online roles.** The package root signs the targets document directly; there are no snapshot or timestamp roles, because those need online keys. Freshness comes from `expires` plus the monotonic metadata version. Part 1 checks expiry when a package is imported; whether decisions also check it is open decision 1.
3. **A mapping change is a meaning change.** Mappings sit inside the definition, so they are covered by the definition digest that ActionIR and approvals bind (HR-030).
4. **Untrusted text is not in the policy environment.** `text` parameters are carried in ActionIR but are not visible to policy CEL, so they can never change scope (HR-023). They cannot be material, and they cannot appear in approval templates.
5. **No floats anywhere.** Packages reject YAML floats, mapping input rejects non-integer JSON numbers, and CEL rejects `double` literals and ordering on `double`/`dyn`.
6. **Irreversible definitions declare a semantic dedupe key** as canonical fields, for example `[target.id, params.amount]`. The key is a hash of their canonical values, so it is the same on every channel (F099) and reformatting an amount cannot change it (HR-007).
7. **Policies only restrict.** No rule kind produces `ALLOW`. An `ANNOTATE` error never changes the verdict but is shown in the checklist. If approval and step-up are both required, the verdict is `REQUIRE_APPROVAL` and both requirements are listed (F071 tracks them separately).
8. **Cost defaults (configurable per tenant):** at most 10,000 runtime cost units per expression, a per-evaluation budget of 100,000, comprehension nesting ≤ 2, expressions ≤ 4 KiB. A rule whose estimated maximum cost exceeds the per-expression limit is refused at compile time.

**Open decisions for the founder.** Each one says which code it blocks (GATES_AND_REVIEW §5). None of them blocks part-1 code, so part 1 proceeds; the recommendations are proposals until confirmed.
1. **Package metadata expiry.** Recommended: 180 days, checked only when a package is imported. Part 1 checks expiry at import, which is needed under either option. The alternative, also checking on every decision, is stricter but turns a missed re-signing into an outage for every customer. *Blocks:* part-2 decision-pipeline code that would read the expiry, and the default validity period of a future `pclaw-admin` signing command.
2. **Signing customer-defined packages (F361/F372, Team).** Recommended: org admins register an org package-signing public key, and activation is a separate, audited step. Alternatives: an online server key, or unsigned packages with two-person activation. *Blocks:* importing customer-authored packages; part 1 trusts only the embedded PantherClaw package roots.
3. **A development package root before Day-0 item 6.** Recommended: none in part 1, which uses throwaway test keys in tests only. A loopback-only development root, like the M1.5 development gateway, can arrive when packages are wired into the gateway. *Blocks:* any development root.
4. **CEL cost limits** (decision 8). HR-043 requires limits under any choice, so part 1 ships the recommended numbers as configurable values, not fixed constants. *Blocks:* nothing; changing them is a configuration change, and part 2 revisits them with measurements.
